# VGGT 3D 스캐너 — 작업 인수인계

## 무엇을 만드는가

물체를 여러 각도에서 찍은 사진 → 3D 점군 → 치수가 들어간 기술 도면(PDF) + STL.

**젯슨**(촬영·출력) + **노트북**(계산)의 2대 구성. 젯슨이 노트북을 네트워크에서 자동으로
찾아 사진을 HTTP로 보내고, 노트북이 VGGT-1B로 복원해서 점군을 돌려준다.

대상 노트북: RTX 4070 Laptop (VRAM 8.6GB) / Ryzen 9 7940HX / RAM 16GB / Windows 11.

## 원본(v1) 대비 바뀐 것

### 1. 가로세로 비율 왜곡 — 가장 중요한 수정
v1은 `load_and_preprocess_images` 출력에 `size=(res, res*1.357)`을 강제로 씌웠다.
1280×720 사진이면 load_fn이 **518×294**를 주는데 이걸 **700×518**로 늘렸다.

```
518x294 (비율 1.76) -> 700x518 (비율 1.35) = 세로로 1.30배 왜곡
```

복원된 물체가 세로로 30% 늘어나 도면 치수가 그만큼 틀렸다. 지금은 `prep_images()`가
비율을 유지한 채 줄이기만 한다. 부수 효과로 픽셀 수가 2.4배 줄어 메모리도 아낀다.

**검증 완료** — 모든 카메라 비율에서 왜곡 3% 이내, 전부 14의 배수.

### 2. 장수·해상도 제한 해제
v1: `files[:max_imgs]` — 8GB 프로파일이면 **10장에서 잘라내고 나머지는 조용히 버렸다.**
해상도도 392로 묶여 있었다.

지금: 장수 제한 없음, 해상도 상한 518(VGGT 학습 해상도, 그 이상은 무의미).
VRAM에 안 들어가면 chain2의 묶음 체이닝(umeyama 정합)으로 이어붙인다.
`setup_laptop.py`의 프로파일에 `"chain"` 플래그가 원래 있었지만 읽는 코드가 없었다.

### 3. 체이닝을 chain2.py에서 server.py로 이식
`umeyama`, `align_windows`, `build_groups`, `remove_ground_ransac`, `find_plane`,
`cam_centers_from_pose_enc`. 젯슨 로컬 계산 경로는 제거했다.

**검증 완료** — umeyama 복원 오차 4.4e-16, 3창 체이닝이 기준 좌표계 복원 1.6e-14,
묶음 분할이 n=7~100에서 전 프레임 커버.

### 4. 후처리를 서버로 흡수
최대거리 필터 · 바닥 평면 RANSAC · kNN 노이즈 · mm 스케일. 로컬 경로를 없앴으니
서버가 이걸 갖지 않으면 기능이 통째로 사라진다.

kNN은 `n_jobs=-1`(기본 1코어였음), 점 수 상한 80만(100장이면 kNN 배열이 828MB).

### 5. poses.json 기반 스케일 (`fit_to_poses`)
리그가 명령한 카메라 좌표(mm)에 VGGT 추정 카메라 중심을 umeyama로 맞춘다.
얻는 것 셋: ① mm 배율 확정 ② 점군이 리그 좌표계로 정렬(up축 자동) ③ **잔차 = 품질 지표.**

**검증 완료** — 완벽 복원 시 잔차 2e-13mm, 좌표 오차 σ=1/5/20mm → 잔차 1.7/8.9/32.8mm.

### 6. SAM 3 통합 — VGGT '뒤'에 붙는다
배경을 지운 이미지를 VGGT에 넣으면 프레임 간 정합 단서가 사라져 포즈가 무너진다.
그래서 **원본으로 VGGT를 돌리고, 나온 점군을 마스크로 거른다.**
`world_points`가 (H,W,3) 픽셀당 3D 점이라 2D 마스크가 1:1로 대응한다.

transformers 경로(`Sam3Model`/`Sam3Processor`)를 쓴다. 네이티브 `sam3` 패키지는
`torch==2.10.0+cu128`을 요구해서 VGGT 환경을 깨뜨린다.

프롬프트를 비우면 **중앙 박스** 방식(첫 프레임 중앙 60% → 이후 직전 마스크 bbox 물려줌).

8GB에 VGGT(3.2GB)가 이미 올라가 있어서, SAM이 OOM 나면 VGGT를 잠깐 CPU로 내렸다가
되돌린다. SAM 실패는 치명적이지 않다 — 마스크 없이 진행한다.

### 7. 런처 앱
`VGGT-Server.bat` 하나로 설치/실행. 배치는 **ASCII 전용**(cmd가 한글 배치를 깨뜨림 —
실제로 `'조직만' is not recognized` 발생 확인). 한글은 전부 파이썬이 출력한다.
바탕화면 경로는 `[Environment]::GetFolderPath('Desktop')`로 얻는다
(OneDrive 리다이렉트 환경에서 `%USERPROFILE%\Desktop`은 낡은 경로).

## GOF 경로 (2026-09-02 추가)

기존 메쉬 경로는 점군 → **Poisson** → STL 이다. 그와 별개로
점군 → **GOF**(Gaussian Opacity Fields) → 메쉬 → STL 경로를 붙였다.
기존 경로는 손대지 않았다 — `colmap_pipe.run_all` 은 그대로다.

| 파일 | 역할 |
|---|---|
| `gof_prep.py` | 사진 → 포즈 + 초기점군 → GOF 데이터셋(COLMAP sparse 규약) |
| `gof_pipe.py` | 데이터셋 → GOF 학습 → 메쉬 추출 → 정리 → STL |
| `gof_setup.py` | GOF 진단 + clone (확장 빌드는 못 한다 — 아래) |
| `GOF-Build.bat` | **CUDA 확장 빌드.** vcvars64 환경이 필요해 bat 로만 가능 |
| `GOF-Setup.bat` / `GOF-Run.bat` | 더블클릭 진입점 |

실행 순서: `GOF-Setup.bat`(받기) → `GOF-Build.bat`(빌드) → `GOF-Run.bat`(스캔).

### 왜 prep 과 pipe 로 나눴나
GOF 는 점군→메쉬 변환기가 **아니다**. 3DGS 계열이라 사진을 다시 렌더해보며
가우시안을 최적화한다. 그래서 사진 + 포즈 + 초기점군이 한 세트로 필요하고,
점군만으로는 못 돈다. 그 조립이 prep 이다.

학습이 30~60분이라, 좌표계가 어긋난 걸 학습 끝나고 알면 최악이다.
그래서 prep 이 끝날 때 **디스크에 쓴 것을 되읽어** 점군을 각 카메라로
재투영하고 화면 안에 떨어지는 비율을 본다 (`verify_dataset`).

### 점군과 포즈는 같은 실행에서 나와야 한다
COLMAP 도 VGGT 도 매 실행마다 좌표계를 새로 잡는다. `_out/object.ply` 같은
예전 결과물은 work 폴더가 이미 지워져(`keep_work=False`) 짝이 되는 포즈가 없다.
그래서 prep 은 포즈와 점군을 항상 함께 뽑는다. `--ply` 로 갈아끼울 수는 있지만
**같은 실행에서 나온 것만** 유효하다.

### 실측 (0831_2058, 133장)
| | 결과 |
|---|---|
| COLMAP 경로 | **110~128s** · 133장 중 116~118장 정합 · sparse 약 21,000점 |
| 〃 재투영 검증 | 카메라 앞 98.4~98.6% · 화면 안 81.8~82.6% (최소 71.7%) |
| VGGT 경로 (`--every 8`, 17장) | **61s** · 300,000점 · 518×294 |
| 〃 재투영 검증 | 카메라 앞 94.8% · 화면 안 60.7% (최소 3.9%) |
| GOF 학습 (VGGT 17장, 1000 iter, `-r 1`) | **133s** |
| GOF TSDF 추출 + STL | **8s** · 삼각형 9,785 · 80mm 앵커 정확 |

STL 검증(trimesh): 정점 5,259 · 면 9,785 · bbox 59.99×80.0×74.19mm ·
법선 감김 일관 · 중복 정점 0. watertight 는 아니다 — 1000 iter 짜리
스모크 테스트라서다(안 본 영역은 TSDF 가 구멍으로 남긴다).

SfM 은 실행마다 결과가 조금 다르다 — 같은 폴더에서 모델 1개(118장)가 나오기도,
2개로 쪼개져 큰 쪽(116장)을 고르기도 했다. `colmap_pipe.sfm` 의 '가장 큰 모델
고르기' 가 그래서 필요하다.

`--every 4` (34장) 로 솎으면 COLMAP mapper 가 `No good initial image pair`
로 죽는다. 링 촬영은 인접 프레임 각도가 이미 커서 솎으면 시차가 한계를 넘는다.
**COLMAP 경로에서는 솎지 마라.** VGGT 는 SfM 이 없어 솎아도 된다(오히려 VRAM 때문에 필요).

### 걸려 넘어진 것 두 가지
1. **`images.txt` 둘째 줄을 빈 줄로 쓰면 안 된다.** GOF 파서는 다음 줄을 무조건
   한 줄 더 읽어서 괜찮지만, `colmap_pipe.read_model` 은 빈 줄을 걸러낸 뒤
   2줄씩 끊어서 **뷰가 정확히 절반으로 조용히 줄어든다** (17 → 9로 실측됨).
   더미 관측 `0 0 -1` 을 넣어 해결.
2. **`plyfile` 이 venv 에 없다.** 초기 점군 ply 는 numpy 로 직접 쓴다
   (3DGS `fetchPly` 가 찾는 x,y,z/nx,ny,nz/red,green,blue 배치를 그대로).

### 설치 상태 — 2026-09-03 기준 동작함
전 경로가 이 PC 에서 실제로 돌았다. VGGT → GOF → 메쉬 → STL 까지.

| | |
|---|---|
| CUDA Toolkit | **12.6** (`winget install Nvidia.CUDA --version 12.6`, 관리자 필요) |
| CMake | 4.4.3 (사용자 범위) |
| GOF | `%USERPROFILE%\gaussian-opacity-fields` · `GOF_DIR`/`GOF_PYTHON` 환경변수 설정됨 |
| diff-gaussian-rasterization | 빌드됨 |
| simple-knn | 빌드됨 |
| tetra-triangulation | **안 빌드함** — 필요 없다(아래) |

빌드는 `GOF-Build.bat` 이 한다. `gof_setup.py` 로는 안 된다 — vcvars64 환경이
필요해서 파이썬 스크립트에서 못 한다.

### 윈도우에서 걸린 것 전부 (하나씩 다 밟았다)
1. **`nvcc` 없음.** torch 의 cu124 는 런타임이라 컴파일러가 없다. 툴킷 3GB 별도.
   CUDA 13.x 는 안 된다 — torch cu124 와 메이저가 안 맞는다. 12.6 을 쓸 것.
2. **`cl.exe` 못 찾음.** `vcvars64.bat` 을 call 해야 한다.
3. **빌드 격리.** `pip install` 이 만든 격리 환경에 torch 가 없어 `setup.py` 가
   죽는다 → `--no-build-isolation`.
4. **`invalid command 'bdist_wheel'`.** 격리를 끄면 venv 의 `wheel` 을 쓰는데 없었다
   → `pip install -U setuptools wheel`.
5. **`DISTUTILS_USE_SDK` 미설정.** vcvars 를 부른 뒤에는 torch 의 cpp_extension 이
   이걸 요구한다 (VC 환경 이중 활성화 방지).
6. **`u_int16_t` / `u_int32_t` 미정의.** POSIX 타입이라 MSVC 에 없다.
   `forward.cu` 983·1145 행에서 nvcc 가 죽는다.
   → `forward.cu` 에 `#ifdef _MSC_VER` typedef shim 을 넣었다. **로컬 패치다.**
7. **editable 설치로는 `simple_knn` 을 import 못 한다.** `__init__.py` 가 없어
   PEP 420 네임스페이스로 안 잡힌다. 빌드는 성공하는데 import 만 실패해서 헷갈린다.
   → `-e` 빼고 일반 설치.

### tetra-triangulation 은 건너뛴다
`extract_mesh.py` 는 `tetranerf.utils.extension`(CGAL + `CONDA_PREFIX` 의 cnpy)이
필요하다. 그런데 GOF 에는 `extract_mesh_tsdf.py` 가 따로 있고 **torch + open3d 만**
쓴다. `gof_pipe.py` 가 tetra 확장 import 를 시도해보고 없으면 자동으로 TSDF 로 간다
(`--extract auto|tetra|tsdf`). 그래서 CGAL 없이도 STL 이 나온다.

### extract_mesh_tsdf.py 로컬 패치 2건
GOF 원본을 고쳤다. GOF 를 다시 clone 하면 다시 넣어야 한다.
1. **디바이스.** `o3d.core.Device("CUDA:0")` 하드코딩 → 윈도우 open3d pip 휠에는
   CUDA 해시맵 백엔드가 없어서 `CreateDeviceHashBackend` 로 죽는다.
   `o3d.core.cuda.is_available()` 로 보고 CPU 로 떨어지게 했다(느리지만 결과는 같다).
2. **복셀 크기.** `voxel_size = 0.002` 하드코딩 → DTU 처럼 정규화된 장면 기준이다.
   여기 COLMAP 장면은 165 단위라 축마다 8만 복셀을 요구해 `block_count` 를 넘긴다.
   `--voxel_size` 인자로 뺐고, `gof_pipe.py` 가 초기 점군 최대변/512 로 넣어준다.

### 8GB 에서 학습 설정 — 반드시 증식을 묶어라
가우시안이 VRAM 을 채우면 **처리량이 7배 붕괴한다.** 실측(0831_2058, 116장):

| 설정 | 속도 | VRAM | 결과 |
|---|---|---|---|
| `-r 2`, 기본 증식 | — | 7993MiB 고정 | **8시간 39분 돌고 미완** |
| `-r 4`, 임계 0.0004 | 22 → **1.3 it/s** (13분째 붕괴) | 2466 → 7967MiB | 중단 |
| `-r 4`, 임계 0.001 + `densify_until_iter 4000` | **22 it/s 유지** | **747MiB** | 11분 완주 |
| `-r 2`, 임계 0.0006 + `densify_until_iter 8000` | 7.8 it/s 유지 | 2835MiB | 29분 완주 |

`-r` 을 낮추는 것만으로는 못 막는다. 붕괴 시점을 미룰 뿐이다.
`--densify_until_iter` 로 가우시안 수를 **묶어야** 속도가 평평하게 유지된다.
`gof_pipe.py --train-extra "..."` 로 넘긴다.

### ⚠ 복셀 크기가 메쉬 해상도를 지배한다 (가우시안 수가 아니다)
`scene_voxel()` 초기 구현이 점군 **전체 min/max** 로 복셀을 잡았는데, COLMAP
sparse 점군에는 배경·오정합 점이 멀리 흩어져 있어 bbox 가 물체보다 훨씬 크다.

    전체 min/max   122.26   <- 이걸 쓰면 복셀 0.2388
    5~95 퍼센타일    9.25
    실제 물체        7.50   <- 물체를 가로지르는 복셀이 31개뿐

그래서 학습을 4배 더 시켜도(686s → 1764s) 삼각형이 2,907 → 3,053 으로 5% 밖에
안 늘었다. 퍼센타일로 고친 뒤 **같은 학습 모델에서 26초 만에 936,411 삼각형**이
나왔다. 307배다. 학습을 늘리기 전에 이걸 먼저 확인할 것.

### SAM 물체 분리 — `--sam` (2026-09-03)
`gof_prep.py --sam [--sam-prompt "..."]` 로 초기 점군에서 물체만 남긴다.
`sam_mask.py` 와 `colmap_pipe.filter_by_masks` 를 그대로 재사용한다
(그 함수의 '2% 미만이면 프롬프트가 틀린 것' 경고까지 같이 얻는다).
마스크는 `<out>/sam_masks.npz` 에 캐시한다 — SAM 이 2분 걸려서, 필터 파라미터만
바꿔 다시 볼 때 재사용한다. 캐시가 현재 이미지 목록을 다 안 덮으면 버리고 다시 만든다
(SfM 등록 장수가 실행마다 116/117/118 로 달라진다).

**⚠ sparse 점군에는 SAM 을 걸어도 소용없다.** 실측(0831_2058):

    sparse 21,001점 -> 마스크 필터 후 10점
    frac 90퍼센타일 0.093 ≈ 마스크 면적 비율(7.3%)

즉 물체 위에 sparse 점이 아예 없다. 물체(스테퍼 모터)가 무텍스처라 SfM 이
특징점을 못 잡는다. 배경·리그에만 점이 생긴다. **`--dense` 와 같이 써야 한다**
(기존 colmap_pipe 도 sparse 가 아니라 fused.ply 를 거른다).

**⚠ 중앙 박스 모드(빈 프롬프트)는 이 리그에서 실패한다.**
물체가 큰 검은 드럼 위에 얹혀 있어서, 중앙이 드럼으로 꽉 차면 SAM 이 배경의
빨간 바닥을 집는다. 프레임별 물체 비율이 0.6~23% 로 요동쳤고, 그 결과
어떤 점도 116뷰 중 24뷰 넘게 마스크 안에 못 들어가 dense 를 걸러도 **0점**이 남았다.

텍스트 프롬프트를 쓰면 해결된다. 10장 표본 비교:

| 프롬프트 | 그럴듯한 프레임 | 비율 표준편차 |
|---|---|---|
| (중앙 박스) | 들쭉날쭉 0.6~23% | — |
| `the stepper motor` | 7/10 | 3.6 |
| `the silver metal motor` | 8/10 | 3.2 |
| **`the small metal device mounted on the black drum`** | **9/10** | **2.4** |

이 프롬프트로 dense 를 거른 결과:

    frac 90퍼센타일 0.078 -> 0.974
    1,232,480점 -> 263,074점 (이상치 제거 후 253,701)
    점군 크기 83~208 단위 -> [1.86, 1.77, 2.05]

**전체 실행 전에 프롬프트를 표본 10장으로 먼저 검증해라.** dense 는 62분이고,
프롬프트가 틀리면 그게 통째로 날아간다.

### ⚠ 점군만 거르면 부족하다 — 이미지 알파까지 구워야 한다
점군에서 배경을 빼도 GOF 는 **마스크 안 된 원본 이미지**로 학습하므로 배경까지
모델링한다. 그러면 extract_mesh_tsdf 가 장면 전체를 물체용 미세 복셀로 담으려다
죽는다. 실측: voxel 0.0026 에서 Open3D 가 9.8GB 를 할당하려다 `exit 0xC0000005`,
복셀을 3배 굵혀도(0.008) 똑같이 죽었다. **복셀 문제가 아니라 범위 문제다.**

해결책은 GOF 코드에 이미 있다.
  - `scene/cameras.py`: RGBA 이미지면 알파를 `gt_alpha_mask` 로 넣는다
  - `extract_mesh_tsdf.py`: `depth[gt_alpha_mask < 0.5] = 0` 으로 배경을 버린다

그래서 `gof_prep.bake_alpha()` 가 SAM 마스크를 알파 채널로 구워 RGBA PNG 로 저장하고
`images.txt` 의 NAME 도 `.png` 로 고친다(3DGS 가 그 이름으로 파일을 찾는다).
마스크가 없는 프레임은 아예 뺀다 — 알파가 없으면 그 프레임만 배경까지 학습해
TSDF 에 배경이 새어든다.

재투영 검증이 바로 좋아진다:

    카메라 앞 98.7% -> 100.0%
    화면 안  82.8% -> 99.9%  (최소 82.6% -> 98.2%)

### ⚠ VGGT 포즈는 GOF/3DGS 에 쓰기엔 정밀도가 부족하다 (2026-09-04 실측)
VGGT 경로 결과가 COLMAP 대비 크게 나쁜 이유를 추적한 결과다.
**VGGT 가 나쁘다는 뜻이 아니다** — 요구되는 정밀도의 종류가 다르다.

같은 사진 115장에서 VGGT 포즈를 COLMAP 포즈에 similarity 정합해 비교:

| | 133장 전체 | 17장 (8장에 1장) |
|---|---|---|
| 카메라 위치 잔차 | 중앙값 **2.43%** · 최대 23.0% | 중앙값 6.41% · 최대 47.8% |
| 카메라 방향 오차 | 중앙값 **3.46°** · 최대 34.6° | 중앙값 17.77° · 최대 70.0° |

프레임을 줄이면 급격히 나빠진다(17장은 방향 오차가 5배). **VGGT 는 절대 솎지 마라.**
그런데 133장을 다 넣어도 방향 오차 중앙값 3.46° 다.

3DGS 계열은 서브픽셀 포즈 정확도를 전제로 한다. 518px 폭에 화각 약 55° 면
3.46° 는 화면상 **약 30픽셀** 어긋남이다. 가우시안이 한 점으로 수렴하지 못하고
여러 뷰의 평균으로 뭉개진다. 실측 증거:

    학습에 쓴 바로 그 사진을 재현한 PSNR = 21.0 dB
    (정상적으로 수렴하면 학습뷰는 30~40 dB)
    렌더가 흐릿하고 물체 위치가 밀려 있음 -> 메쉬도 파편화

즉 **메쉬 추출이 깨진 게 아니라 가우시안 자체가 안 맞은 것**이다.
extract_mesh_tsdf 를 아무리 손봐도 해결되지 않는다.

VGGT 의 강점인 '한 번에 나오는 조밀한 깊이/점군' 은 이 정밀도를 요구하지 않는다.
스캐너에서 VGGT 점군이 쓸 만했던 것과 여기서 GOF 가 실패하는 것은 모순이 아니다.

**고치려면 포즈를 다듬어야 한다.** COLMAP 의 `point_triangulator` +
`bundle_adjuster` 에 VGGT 포즈를 초기값으로 넣어 BA 를 돌리는 방법이 있다.
COLMAP SfM 이 조각나는 데이터셋에서 특히 값어치가 있다(0831_2058 도 모델이
2개로 쪼개졌다). 다만 특징점 추출·매칭은 어차피 해야 해서, 정합이 잘 되는
데이터셋이라면 그냥 COLMAP SfM 을 쓰는 것과 비용 차이가 크지 않다.

### BA 로 VGGT 포즈 다듬기 — `gof_ba.py` (미완성, 2026-09-04)
VGGT 포즈를 초기값으로 COLMAP `point_triangulator` + `bundle_adjuster` 를 돌려
정밀화하려 했다. **아직 동작하지 않는다.** 판단 근거는 대조 실험이다.

**대조 실험이 핵심이다.** COLMAP 자기 포즈를 넣고 같은 경로를 태워봤다.
BA 는 이미 최적인 그 포즈를 거의 그대로 보존해야 한다(0.01도 수준).

| 시도 | 대조군 방향 오차 중앙값 |
|---|---|
| 최초 | 1.079도 |
| 내부 파라미터 고정 후 | **0.644도** |
| (정상 기대치) | ~0.01도 |

즉 하네스가 아직 정상 포즈를 망가뜨린다. **그래서 "BA 가 VGGT 를 개선하는가"
라는 질문에 아직 답할 수 없다** — VGGT 로 잰 수치는 전부 이 버그를 측정한 것이다.
대조 실험을 먼저 통과시킨 뒤에 VGGT 를 재라.

고친 버그들 (각각 실제로 개선됨):
1. **`rot2qvec` 부호 오류.** 손으로 옮겨 적다 마지막 행 부호를 뒤집었다.
   회전 왕복 오차 1.89(정상 1e-16) → BA 결과 3.46도가 87.79도로 폭발했다.
   **직접 다시 쓰지 말고 `gof_prep.rotmat2qvec` 을 import 해라.**
2. **반복 루프가 BA 출력을 그대로 다음 삼각측량에 넣었다.** 그 모델엔 이미
   3D 점·관측이 있어 중복 누적으로 퇴화한다. 대조군 카메라 배치 크기가
   9.11 → 9.13 → 22.8 → 191,242 → 4.6e7 로 발산했다.
   포즈만 남기고 점을 비워 넘겨야 한다(`write_prior_model` 재사용).
3. **삼각측량 임계값.** `tri_create_max_angle_error` 기본 2도인데 VGGT 오차가
   3.46도라 대응점 대부분이 버려졌다(3,781점). 12→6→3→2도로 조여가니 21,000점.
4. **BA 를 데이터셋 이미지(518x294)로 돌리면 안 된다.** 특징점이 이미지당
   105개뿐이다. 원본 1920x1080 로 돌리면 9,358개. `--src-images` 로 넘긴다.
5. **내부 파라미터 자유도.** 초점거리·왜곡을 함께 흔들면 포즈와 맞바꾸며 헤맨다.
   기본을 고정으로 바꿨다(`--fit-intrinsics` 로 해제).

**남은 유력 용의자**: BA 를 '왜곡이 있는 원본 사진' 으로 돌리면서 왜곡 계수를
0 으로 고정해 뒀다. 화면 가장자리 특징점의 재투영 오차를 BA 가 카메라를
움직여 흡수한다. 다음 시도는 **undistort 된 이미지 + 정확한 undistorted 내부
파라미터**로 BA 를 돌리는 것이다.

### 알파 마스크는 학습 이미지에 곱해지지 않는다 (GOF 의도)
`scene/cameras.py:44` 에서 `original_image *= gt_alpha_mask` 가 **주석 처리**돼 있다.
알파는 저장만 되고 `extract_mesh_tsdf.py` 가 배경 깊이를 버리는 데만 쓴다.
그래서 학습은 배경까지 포함해서 돈다(가림 관계를 맞추려는 설계로 보인다).
`gt_1/` 로 덤프한 학습 이미지에 배경이 그대로 보이는 게 정상이다.

### 치수는 여전히 앵커가 필요하다
GOF 는 사진에 맞춰 표면을 최적화하니 형상은 Poisson 보다 낫지만,
**스케일은 입력 포즈에서 그대로 상속된다.** VGGT 포즈로 돌리면 VGGT 의
스케일 오차를 물려받는다. `gof_pipe.py --size-mm <최대변 mm>` 로 앵커를 걸어라.

## 미해결 / 다음 작업

1. **성능 회귀 미해결.** 사용자가 "수정 전이 훨씬 좋았다"고 보고. 같은 사진 폴더인데
   결과가 나빠졌다. 원인 미확정 — 서버 로그를 못 받아서 추측만 한 상태.
   확인할 로그 줄: `[SAM 3]`, `물체 비율 N%`, `평면1:`, `[바닥평면 제거]`, `N장 → 묶음 N개`.
   **server.py는 재시작해야 반영된다** (파일만 덮어쓰면 옛 코드가 계속 돈다).

2. **바닥 슬래브 두께 설계.** `thickness`가 장면 대각선에 비례한다. 배경이 넓으면
   슬래브가 두꺼워져 작은 물체(마우스 크기)가 통째로 지워진다. 2~98 퍼센타일로
   완화했지만 근본 해결은 아니다. 평면 inlier 분포(3×MAD 등)에서 두께를 유도하는 게 맞다.

3. **리그 하드웨어.** `rig.py`의 `RigController.move_to()` 하나만 구현하면 된다.
   그전까진 ManualRig로 좌표 기록 효과를 그대로 얻는다.

4. **VGGT-Ω 이관 보류.** 메모리가 프레임 수에 선형(고정 5.94GB + 74MB/장)이라
   100장 단일 패스가 가능하지만 두 가지 걸림돌:
   - **FAIR Noncommercial License — 상업적 사용 금지** (원본 VGGT는 상업 사용 허용)
   - `world_points`가 없다 (`depth`/`pose_enc`만) → 언프로젝션 직접 구현 필요
   8GB에서는 고정비 5.94GB 때문에 fp32면 12장뿐이라 이점도 작다.

5. **`scan.py`의 잔차 5mm 기준**은 임의로 정한 값. 실측으로 조정 필요.

## 실행

**노트북**: 5개 파일 한 폴더 → `VGGT-Server.bat` 더블클릭 (첫 실행 20~40분)
**단독 테스트**: 서버 켜둔 채 `VGGT-Test.bat` (사진 폴더 끌어다 놓기)
**젯슨**: `~/vggt/`에 풀고 `python3 scan.py`

설치 경로는 `%USERPROFILE%\vggt_server\` (venv·모델·vggt 소스). `venv`는 절대경로가
박혀 있어 다른 PC로 복사하면 깨진다. `VGGT-1B\` 폴더만 복사하면 4.7GB 재다운로드를
건너뛸 수 있다.

SAM 가중치 접근은 HF **계정 단위 승인**, 로그인 토큰은 **윈도우 계정 단위** 저장.
